# 第二个项目：When 导读（第六到八周 · 第 33—54 节）
> 这份导读帮助学员快速看清：每节讲什么、重点是什么、和前后课程怎么衔接。
>
> 标注 **「执行课」** 的课程以现场运行 Loop、观察测试结果和解决问题为主，不再增加新的生产模块讲义；目录中的 MD 是执行手册。
---
## 一、内容设计思路
When 是实战营的第二个项目。我们用三周完成一个**独立、通用的分布式延时投递组件**：业务方提交一条消息和到期时间，When 负责可靠保存、按时触发，并把消息投递到 HTTP、Kafka 等下游。
它与第一部分 OryxOS 刻意形成对照：OryxOS 主要练习如何借助 Spec-Kit，在人的持续检查下逐步完成项目；When 进一步练习 Loop Engineering——先把目标、公共契约、模块任务、实现边界和自动化验收准备清楚，再让 AI 在“实现 → 测试 → 修正”的循环里持续推进。
这里所说的 **Loop 原料**，不是一段宽泛的提示词，而是一份可以执行的模块任务规格，至少包含：
- 这一模块要解决什么问题；
- 它依赖什么、交付给谁；
- 接口、字段和行为规则；
- 哪些事情明确不做；
- 必须通过哪些自动化测试；
- Loop 运行时必须遵守哪些 Harness 约束。
所以这三周会把大量时间花在“运行之前”。原因很直接：规格含糊，AI 会自行补全；接口不统一，各模块会分别做对、最后拼不起来；测试不能自动判断，Loop 就不知道什么时候算完成。前面的设计质量，决定后面的循环能否真正跑通。
课程不会把整个 When 一次性扔给 AI 后等待结果，而是安排两次边界清楚的运行：
1. **第 46 节第一次运行**：学员只提交一个提示词。Codex 先在 `lesson/46` 开发并合并 Runner，随后自行执行 `./loop run`；Runner 按第 39—45 节逐节开发，每节使用独立分支并在通过后合并 `master`，最后完成第一阶段整体验收。
2. **第 53 节第二次运行**：在第一次运行的基线上加入副本、Controller、真实 Sink、可观测、管理台和部署，验收完整 HA。
硬约束保持不变：核心代码 90% 以上由 AI 产生，全程有人评审；验收不能只看演示效果，必须保留构建、测试、指标、日志和故障时间线等机器可验证的证据。

## 二、三周地图
- **第六周（33—39）｜认知、方法与公共底座**  
  分布式原理 → OryxOS 与 When 对比 → Loop 与 Harness → 技术评审 → When 的 Loop 模型 → 自动化验收体系 → 公共模型与模块接口。
- **第七周（40—46）｜第一批模块原料与第一次运行**  
  gRPC 契约 → Redis 存储 → ETCD 元数据 → 节点集群 → 时间轮 → 接入路由 → 建立根工程并整合 Harness → 第一次执行 Loop。
- **第八周（47—54）｜完整 HA、真实投递与第二次运行**  
  副本恢复 → Controller → HTTP/Kafka Sink → 可观测 → Web 管理台 → 部署与 CI → 完整 HA 联调 → 总结与社区推进。
三周的主线可以压缩成一句话：
```text
先理解问题和架构 → 定公共契约 → 写可验证的模块任务 →
第一次跑出核心链路 → 补齐 HA 与生产能力 → 第二次跑完整系统
```

## 三、关于 Loop：为什么功夫主要在运行之前
Loop 不是“按一次回车，AI 自动写完整个项目”。它能持续工作的前提，是环境中已经存在清楚的输入和可靠的自动验收。
When 为 Loop 准备五层输入：
1. **项目基准文档**：业界调研、需求文档、技术方案和 AI 编程实施指引；
2. **公共底座**：`Message`、状态机、SPI、`ClusterView`、`TimeWheelRegistry`、`DueMessageHandler`；
3. **模块任务规格**：每节的功能、接口、边界、Harness 和验收；
4. **工程结构与启动规则**：固定 Maven 模块、唯一 Composition Root、启动和停机顺序、静态时间轮映射；
5. **自动验收**：单元、契约、集成、端到端、故障测试以及 CI 门禁。
人不会从过程中消失。人的职责从逐行执行，转为：确定目标、确认公共契约、设计失败场景、保护验收、判断架构歧义，并在高风险节点进行评审。Loop 负责在这些边界内反复实现和验证。
### 两次运行的边界
| | 第 46 节第一次运行 | 第 53 节第二次运行 |
|---|---|---|
| 输入 | 第 46 节唯一提示词 + 第 39—45 节原料 | 第 46 节基线 + 第 47—52 节 |
| 投递 | `RecordingTestSink` | 真实 HTTP / Kafka Sink |
| 时间轮分布 | 明确配置的静态映射 | Controller 管理的动态分布 |
| 集群范围 | 注册、选主、成员感知、跨节点转发 | 副本、切换、重建、rebalance |
| 主要验收 | 收、存、入轮、到期、查询、取消、重启恢复 | 不丢、至少一次、10 秒切换、完整部署与可观测 |
这样安排不是降低难度，而是让每次失败都有明确归属：第一次先证明零件能够组合，第二次再证明完整 HA 在故障下仍然正确。

## 四、第六周：When 起手——认知、方法与公共底座
### 第 33 节｜分布式 / 集群化架构：原理 + 拆解
- **讲什么**：容量上限、单点故障、成员感知、选主、路由、副本、故障接管和公共协调。
- **重点**：理解分布式不是“多启动几个进程”，而是解决多节点之间谁在线、谁决策、数据在哪、故障后谁接管。
- **衔接**：为 When 后面的 ETCD、Controller、Master/Slave 和路由设计建立基础概念。
### 第 34 节｜OryxOS 的分布式 vs When 的分布式
- **讲什么**：同样是多节点协调，为什么 OryxOS 使用数据库表和抢锁，When 使用 ETCD、时间轮副本与 Redis 恢复。
- **重点**：架构选型取决于及时性、一致性和运维成本，不取决于组件看起来是否高级。
- **衔接**：为第一部分收尾，同时解释 When 为什么需要更完整的在线集群架构。
### 第 35 节｜深聊 Loop 编程与 Harness
- **讲什么**：Loop 的运行方式、五个基本要素、停止条件，以及 Harness 为什么是循环的核心。
- **重点**：没有可自动判断的目标和测试，循环只会更快地放大错误；实现者不能修改或削弱自动验收。
- **衔接**：从“系统怎么设计”转到“怎么让 AI 可靠地实现系统”。
### 第 36 节｜When 技术评审
- **讲什么**：基于需求、业界调研和技术方案，对整体架构、模块边界与核心技术决策进行评审。
- **重点**：确认 Redis 与 ETCD 的责任、时间轮的作用、Master/Slave 的恢复语义、外 HTTP 内 gRPC，以及当前 Java 技术栈。
- **衔接**：技术方案通过评审后，才能继续拆成 Loop 可以执行的模块任务。
### 第 37 节｜设计 When 的 Loop 模型
- **讲什么**：如何拆分模块、安排依赖顺序、组织公共与模块 Harness，以及为什么采用两次运行。
- **重点**：能独立验证的模块可以分开实现，但必须共同依赖一套公共契约；分布式正确性仍需要人在关键点把关。
- **衔接**：确定后面三周的实施顺序和每份模块任务的固定结构。
### 第 38 节｜Loop 下的自动化测试验收体系
- **讲什么**：单元、集成、端到端、故障和性能测试；如何验证不丢消息、切换时延和唯一性。
- **重点**：不追求没有意义的覆盖率数字，而是覆盖真实失败模式；快测试进入每轮 Loop，重测试交给 CI 和人工环境。
- **衔接**：为第 39 节以后每份模块任务中的“自动化验收”提供统一方法。
### 第 39 节｜定义 When 的公共模型与模块接口
- **讲什么**：统一 `Message`、状态机、强类型 `SinkConfig`，以及存储、时间轮、路由和投递模块之间的接口。
- **重点**：除了 `StoragePlugin`、`Sink`、`TimeWheel`、`Router`，还要统一 `TimeWheelRegistry`、`ClusterView` 和 `DueMessageHandler`，避免模块集成时临时发明接口。
- **衔接**：它是第 40 节以后所有模块共同引用的底座。公共契约尚未确定，后续模块不得开工。

## 五、第七周：第一批模块原料与第一次运行
> 从第 40 节开始，每份模块文档同时承担两种作用：帮助学员理解模块，也作为 Loop 的执行输入。固定内容包括职责、依赖、交互、接口、字段、测试、边界、Harness 和交付物。
### 第 40 节｜定义消息操作契约并实现 gRPC 服务骨架
- **讲什么**：用 proto 定义 Submit、Query、Cancel，生成 stub，并实现只负责协议转换、校验和委托的 gRPC Server。
- **重点**：传输契约和内部领域模型分开；Server 不能重复实现发号、路由、存储和状态机。
- **衔接**：为第 45 节应用处理流程和跨节点调用提供稳定入口。
### 第 41 节｜存储层插件化 + Redis 插件
- **讲什么**：实现 `StoragePlugin`、Redis Key 结构、原子状态转换、恢复索引和终态清理。
- **重点**：消息必须先可靠写入 Redis，再进入内存时间轮并返回；按消息拆小 Key，禁止全局大 ZSet/Hash。
- **衔接**：第 44 节依赖它重建时间轮，第 45、47、49 节依赖它取得状态转换权。
### 第 42 节｜元数据存储：ZK vs ETCD 选型
- **讲什么**：为什么选择 ETCD，以及节点、Controller、时间轮和配置分别使用哪些 Key、Lease、Watch 和 Txn。
- **重点**：ETCD 只保存集群事实，不保存消息 payload；Lease 使用 6 秒 TTL、2 秒续约，为 10 秒故障切换预留恢复时间。
- **衔接**：为第 43 节的注册、选主和集群视图提供统一客户端与 Key 空间。
### 第 43 节｜节点集群：注册、组集群、切换感知
- **讲什么**：节点注册和心跳、Controller 选举、成员 Watch，以及 `EtcdClusterView` 如何联合节点和时间轮元数据定位 Master。
- **重点**：本节只完成成员感知和只读集群视图，不执行 Master/Slave 切换，也不做动态 rebalance。
- **衔接**：第 45 节使用集群视图完成跨节点转发；第 47、48 节在成员事件上继续实现 HA。
### 第 44 节｜时间轮：延时机制原理与实现
- **讲什么**：多层时间轮、槽位计算、跨层下移、补偿式调度、取消和从 Redis 重建。
- **重点**：调度线程只移动引用并异步报告到期，通过 `DueMessageHandler` 交接；不删除 Redis、不直接调用 Sink、不执行同步 IO。
- **衔接**：第 45 节负责把消息加入目标时间轮，第 46 节先注入测试到期处理器，第 49 节再替换为真实投递。
### 第 45 节｜接入层 + 路由层
- **讲什么**：参数校验、Snowflake 发号、一致性 Hash、`TimeWheelRegistry`、`ClusterView`、先落库再入轮，以及跨节点 gRPC 转发。
- **重点**：同一条消息的 Submit、Query、Cancel 必须稳定落到同一 `tw_id`；找不到 Master 或本地时间轮时明确失败，不能静默选择默认节点。
- **衔接**：把第 40—44 节连接成一条完整写入链路，为第一次运行做好准备。
### 第 46 节｜Loop 运行演示课：第一次整合运行（执行课）
- **现场做什么**：从只有四份项目文档和课程资料的空项目开始，把唯一提示词交给 Codex。Codex 先在 `lesson/46` 生成并验证 `AGENTS.md`、受保护验收入口和独立 Runner，合并 `master` 后立即自行执行 `./loop run`；Runner 从第 39 节开始依次读取原料，每节都从最新 `master` 创建独立分支，在该分支实现和验收，通过后以 `--no-ff` 合并 `master`，直到第 45 节和最终验收全部通过。中间不需要第二个提示词。
- **配套材料**：《第 46 节附件：Loop Runner 完整使用与实现手册》给出完整配置、命令、状态文件、分支规则、自动重试、断点恢复和排错依据。
- **重点**：外层循环负责选择课程、管理分支、启动本机临时 Redis/ETCD、执行验收和恢复进度；内层循环只处理当前课程的“读取 → 计划 → 实现 → 验证 → 修正”。普通问题由 Runner 根据项目文档、当前课程原料和失败证据继续解决，不等待确认；已经合并 `master` 的课程不会重跑。
- **验收范围**：Submit → Redis → 时间轮 → 测试到期处理 → DELIVERED；Query/Cancel；重启恢复；唯一 Controller；跨节点转发；节点下线感知。
- **明确不做**：真实 HTTP/Kafka Sink、Master/Slave 切换、动态 rebalance 和完整 HA。
- **运行约束**：不用额外工作目录，不使用容器。Redis、ETCD 由 Harness 以本机临时进程启动，使用随机端口和临时数据目录，成功、失败或中断后都自动停止。
- **衔接**：运行中出现的问题在当前课程分支内根据对应原料解决；本节验收通过并合并 `master` 后，才进入下一节。

## 六、第八周：完整 HA、真实投递与第二次运行
### 第 47 节｜故障恢复：Master/Slave 副本同步
- **讲什么**：Master 异步同步 Slave、操作顺序与去重、out-of-sync 标记、从 Redis 重建、分配版本和旧 Master 隔离。
- **重点**：副本用于快速接管，Redis 才是消息最终恢复来源；系统保证至少一次，不承诺故障窗口绝不重复。
- **衔接**：提供“怎么同步、怎么提升、怎么恢复”的执行能力，交给第 48 节 Controller 决策。
### 第 48 节｜故障恢复：Controller
- **讲什么**：Controller 处理节点加入、离线、Slave 不同步和负载变化，生成提升、补副本和 rebalance 计划。
- **重点**：决策与执行分离；所有分配变化通过带 Controller term 和 ETCD revision 检查的事务提交。
- **衔接**：与第 47 节共同完成 Master 故障后 10 秒内接管的流程。
### 第 49 节｜Sink 投递插件化：HTTP + Kafka
- **讲什么**：Java SPI、HTTP Sink、Kafka Sink、Producer/客户端复用、失败分类和指数退避。
- **重点**：实现生产 `DefaultDueMessageHandler`，补上投递租约与过期恢复；HTTP 限制危险地址和响应大小，Kafka 区分临时错误与永久错误。
- **衔接**：消息生命周期从“测试成功”变为真实投递，下游通过 `message_id` 处理至少一次带来的重复可能。
### 第 50 节｜可观测体系：Metrics、日志与健康检查
- **讲什么**：Prometheus 指标、包含 `trace_id` 的结构化日志、`/metrics`、`/health`、`/ready`。
- **重点**：关键路径和故障场景都有证据；指标禁止使用 `message_id/trace_id/tw_id` 等高基数字段作为 label，异步线程不能丢失或串用 trace ID。
- **衔接**：为管理台、Kubernetes 探针和第 53 节故障演示提供观测依据。
### 第 51 节｜Web 管理台
- **讲什么**：时间轮、消息、投递详情和集群页面，以及对应的 admin HTTP API。
- **重点**：管理台是独立静态前端；消息列表使用有界分桶索引和游标分页，不执行全库扫描，也不展示 payload 和敏感配置。
- **衔接**：让第 53 节联调过程可以被观察，而不是只能依赖终端日志。
### 第 52 节｜部署与 CI：docker-compose、Kubernetes
- **讲什么**：本地、单节点和 Kubernetes 三种部署方式，StatefulSet 节点身份、worker ID、健康探针、优雅退出、滚动升级、镜像和 CI。
- **重点**：部署命令和 CI 使用同一组验收脚本；CI 文件只允许第 52 阶段生成，通过后立即冻结，后续阶段不能修改。
- **衔接**：为第 53 节提供一键启动完整集群和执行最终验收的环境。
### 第 53 节｜Loop 运行演示 · 联调：完整 HA（执行课）
- **现场做什么**：把第 47—52 节加入第 46 节已经跑通的基线，重新部署完整集群并执行最终验收。
- **重点**：使用真实 HTTP/Kafka Sink、动态时间轮分布、Master/Slave、Controller 和完整可观测体系；问题仍然回填原料后从干净状态重跑。
- **验收范围**：提交、查询、取消、真实投递、管理台、杀 Master 后 10 秒内接管且消息不丢、杀 Controller 后重新选举、指标和日志能够证明全过程。
- **衔接**：所有自动验收通过后，When 才从“模块实现完成”进入“可以发布和演示”的状态。
### 第 54 节｜When 项目总结与后续规划
- **讲什么**：项目能力回顾、两次 Loop 运行、Harness 经验、AI 编程总结、后续路线和社区推进。
- **重点**：When 是课程样本；真正要带走的是如何用公共契约、可执行任务、自动验收和人的检查点组织 AI 编程。
- **衔接**：总结第二个项目，并把更多 Sink、鉴权限流、死信、优先级、跨地域、Operator 和 MCP 等能力交给后续社区演进。

## 七、学完这三周，应该真正拿到什么
不是只拿到一套 When 代码，而是拿到一套可以迁移到其他企业项目的方法：
- 从业界调研和需求中确定项目边界；
- 在编码前完成技术评审和公共契约；
- 把复杂系统拆成可以独立实现、独立验收的任务；
- 用 Harness 保护安全、依赖方向、测试和停止条件；
- 用 Composition Root 和整体 Harness 解决“模块分别正确但拼不起来”的问题；
- 用集成测试和故障注入验证分布式正确性；
- 让 AI 承担大部分执行，让人保留架构判断和最终责任。
